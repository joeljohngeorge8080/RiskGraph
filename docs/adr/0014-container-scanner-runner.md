# ADR-0014: Scanners run as hardened containers (DockerRunner), with pinned images

Status: accepted · Date: 2026-10-23 · Implements: roadmap Phases 3 and 4 (blueprint §9.2–9.4) · Supersedes the runtime part of: ADR-0009 (the subprocess runner remains for host development only)

## Context
ADR-0009 ran scanners as host subprocesses, with the worker's uid and no isolation. Blueprint §9.3 requires every scanner to run in a container with a fixed profile (nobody uid, read-only root, no capabilities, no network except where stated, resource limits), and the worker to reach the daemon only through a socket proxy.

## Decision
- **One runner interface, two implementations.** `DockerRunner` implements the same `ScannerRunner` protocol as `SubprocessRunner`. The pipeline gains no branches except runner selection (`RISKGRAPH_SCANNER_RUNNER`). Options considered: the `docker` CLI in a subprocess (no new dependency, but argument building is string-heavy and harder to test) versus the Docker SDK (chosen: typed calls, testable against a fake client, one approved dependency, `docker>=7.1`).
- **Profile in one pure function.** `modules/scanners/containers.py` builds the `containers.create` arguments: uid 65534, `read_only`, `cap_drop ALL`, `no-new-privileges`, `network none` or the named egress network, memory 2g, 1.5 CPU, 512 pids, a 256 MB tmpfs `/tmp`, core dumps and file size capped with ulimits, and no environment beyond an allow-list. It refuses unsafe mounts (relative or `..` paths, duplicates, the Docker socket). Tests cover each refusal.
- **Same paths inside and outside.** A scanner sees each directory at the path the worker uses, so adapter argv and env work unchanged. The worker maps those paths to host paths when it creates bind mounts, because the daemon only knows host paths. The mapping roots come from settings (`RISKGRAPH_HOST_DATA_DIR`, `RISKGRAPH_HOST_TRIVY_CACHE_DIR`), which `make dev` takes from the named volumes' mountpoints. Blueprint §9.3 used `/workspace` and `/out`; this deviates to avoid rewriting every adapter, and the isolation is unchanged.
- **Workspace permissions.** The scanner uid must traverse and write the workspace, so the scan directory is `0711` and the output and HOME directories are writable. Each scan path contains a random UUID, and nothing outside it is shared.
- **Cleanup of container-written files.** Files a scanner writes are owned by uid 65534, so the worker cannot delete them. Before removal the worker widens the directories it owns, and a scanner image runs a small `chmod` pass as nobody (`make_removable`). Removal never depends on that pass succeeding: a refused `chmod` is ignored and the delete still goes ahead.
- **The clone runs in its own image.** `git-fetcher` is the only container with egress during a scan, runs as the worker's uid (so its output can be cleaned up), and mounts only the workspace. It holds no secrets.
- **Trivy runs offline.** Scans use `--skip-db-update` and `network none`. A trusted task (`riskgraph.scanners.refresh_trivy_db`, Beat every 6 h, holding the Trivy lock) is the only egress path for the DB. After a refresh the cache is made world-writable, because Trivy takes a write lock during a scan.
- **Images are pinned.** Every Dockerfile takes its version from `docker/scanner-versions.env` (the only source of truth), verifies release tarballs against the upstream checksums file, and runs as `65534`. `test_scanner_images.py` fails if an adapter's tag drifts from the env file. The base images are pinned by digest. Semgrep and Checkov install from PyPI at pinned versions without hashes (noted as a residual).
- **Socket proxy.** The worker reaches the daemon only through `tecnativa/docker-socket-proxy` (pinned by digest) with `CONTAINERS`, `IMAGES` and `POST` on and everything else off. Residual risk, as blueprint §9.3 states: `POST /containers/create` accepts binds, so a worker compromise is still a host compromise. The proxy uses a read-write socket mount, because connecting to a unix socket needs write access.
- **Slots and lifecycle.** A Redis sorted-set semaphore caps running scanner containers (`riskgraph:scanner_slots`, default 4) with leases, so a dead worker cannot hold a slot. Cancel sets the scan to `CANCELLED` and the worker kills containers by label. A reaper (Beat, every 5 min) times out runs older than twice the longest timeout and fails scans with no progress for an hour.

## Consequences
- Verified live (this host, `make dev`, NodeGoat): all five scanners ran as containers, the scan reached COMPLETED with 124 findings (matching the earlier host run), and no workspace or container was left behind.
- Cleanup now has a second moving part (the fixup image). If the image is missing, the chmod pass is skipped and removal can fail, which is reported in the log.
- Not done: gVisor (blueprint's upgrade path), Kubernetes runners, and the blueprint's `/workspace`/`/out` layout.
- `docker` is a new runtime dependency (approved). Its stubs are not installed; the package is listed under mypy's untyped-import override, like `celery`.
