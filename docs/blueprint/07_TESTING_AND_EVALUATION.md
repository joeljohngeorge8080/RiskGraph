# RiskGraph — Testing Strategy and Research Evaluation (sections 25–26)

## 25. Testing strategy

### 25.1 Layers and markers

| Layer | Marker | Needs | What it covers | Runs |
|---|---|---|---|---|
| Unit | (none) | nothing | parsers (recorded fixtures), fingerprinting, severity mapping, manifest schema, IaC extractors, import/call graph on small source trees, graph builder invariants, attack-graph derivation, path search on hand-built graphs, risk model tables + Hypothesis properties, explain validator golden packs, policy evaluation | every push, < 60 s |
| Integration | `db` | Postgres + Redis (Compose test profile) | repositories/scans services, migrations up/down, dedup index, status transitions, API→Celery enqueue (eager mode), collector→normalizer→DB, graph→risk on stored data, SSE | every push |
| Scanner | `docker` | Docker | each adapter on its dataset dir under the isolation profile; network-none assertion; timeout kill; output size cap | every push on ubuntu runner, nightly full |
| Security | `security` | Postgres | authz matrix (4 roles × every endpoint), login rate limit, refresh reuse detection, webhook signature (valid/invalid/replayed), SSRF URL policy, path traversal from crafted scanner output, command-injection strings in ref/name, secret-exposure grep of DB dump + logs, CSP/header presence, LLM injection golden packs | every push |
| E2E | `e2e` | Docker + services | trigger → scan → findings → paths → risk → (dashboard via Playwright) on `datasets/scenarios/*` | nightly + before release |
| Performance | `perf` | Docker | scan wall time on kitchen-sink; graph load + path search at 5 k/20 k; API p95 under `locust` 50 users | nightly, recorded in `TEST_REPORT.md` |
| Frontend | vitest / playwright | — | components with mocked API; smoke over the demo path | every push / nightly |

Conventions: pytest, `tests/` mirrored per module plus cross-cutting folders;
factories via `factory_boy`; real Postgres (no SQLite substitution, JSONB and
partial indexes differ); Celery `task_always_eager` for API tests, real
worker for E2E; fixtures recorded with the pinned scanner version in the path
so a version bump forces re-recording.

providers reject (documented per key type).

## 26. Research evaluation methodology

### 26.1 Question and hypotheses

**RQ:** Does contextual graph-based prioritization rank practically important
findings higher than CVSS-only and CVSS+EPSS prioritization?

- H1: RiskGraph achieves higher Precision@K and nDCG@K than both baselines on
  the scenario suite (K ∈ {5, 10}).
- H2: RiskGraph requires fewer findings reviewed to reach 90 % recall of
  important findings (analyst effort).
- H3: Each context factor contributes: removing any of {reachability,
  exposure, identity/data, attack-path coupling} reduces nDCG (ablation).
- H0 (fair): with context removed, RiskGraph's ranking equals CVSS+EPSS (sanity check of §14.3).

### 26.2 Methods compared

| Method | Ranking key |
|---|---|
| M1 CVSS-only | CVSS base desc; non-CVE findings by canonical severity mapped to a fixed CVSS-equivalent (secret=high 7.5, etc.) so they are rankable, tie-break by scanner order |
| M2 CVSS + EPSS | `cvss_norm × E` where `E` is §14's EPSS transform (same transform for fairness), non-CVE as M1 |
| M3 DefectDojo-style (stretch) | dedup + severity + KEV flag (approximates what an aggregator gives) |
| M4 RiskGraph | risk score desc |

### 26.3 Ground truth

**Primary (scenario suite):** labels are by construction. Each scenario repo
ships `ground_truth/labels.csv` with `finding_fingerprint, important (0/1),
rationale`. Important = an attacker with Internet access (or the leaked
credential) could plausibly reach confidential data or elevated privilege
through this finding. Roughly 60–120 findings across scenarios with ~15–25 %
positives, so Precision@K is informative.

**Secondary (real apps, stretch):** two independent labellers (the author and
the supervisor or a peer) label the top-30 union of all methods' rankings
blind to method, using a written rubric; Cohen's κ reported; disagreements
adjudicated. **KEV is held out** from M4 during this evaluation (E uses EPSS
only) so KEV cannot be both input and truth; results reported with and
without KEV.

### 26.4 Metrics

Precision@K, Recall@K, nDCG@K (K=5,10), MAP, analyst effort E90 (findings
read to reach 90 % recall), Spearman ρ vs the ideal ranking, attack-path
identification rate (fraction of constructed paths recovered with correct
sink), false-positive reduction (important findings above the Critical/High
threshold vs unimportant ones above it), processing time per stage, scanner
coverage (findings per scanner per dataset).

### 26.5 Statistics

Bootstrap 95 % confidence intervals over findings (2 000 resamples) for each
metric; paired permutation test for M4 vs M2 on nDCG@10 across scenario
repos (few units, so exact permutation); ablation table with deltas; weight
sensitivity: grid over likelihood weights on the simplex (step 0.1) and
threshold sweeps, reporting nDCG surface and whether equal weights are within
the top-decile region (if yes, equal weights are retained). All code in
`evaluation/` runs from stored scan results, seeded, reproducible in one command.

### 26.6 Threats to validity (to be written honestly)

Synthetic scenarios are designed by the same author who designed the model
(construct bias — mitigated by the blind real-app study and by publishing the
scenarios); small N; static context may differ from runtime truth;
reachability blind spots cause under-claims that could favour baselines on
dynamic code; the EPSS transform is shared with M2 by design so the comparison
isolates context, not the transform.
